# Design: Deck Library Consolidation + Per-Slide Prompted Regenerate

**Change:** deck-library-consolidation
**Created:** 2026-08-07

## Technical Approach

Two independent slices, both purely additive to existing surfaces:

1. **Library merge.** `GET /api/library` keeps its existing `Draft` query (with one new AND-condition: `deckSlide: null`) and adds a parallel `Deck` query under `deckVisibilityWhere`. A new pure helper merges the two already-sorted-by-`createdAt`-desc arrays into one sorted, paginated, `type`-discriminated array. No DB-level `UNION`; app-code merge, matching the proposal's recommended v1 approach.
2. **Per-slide refine.** `DeckReviewSlideCard` gets a small, self-contained instruction input (mirroring `RefinementPanel`'s UX, not reusing the component itself — the deck poll has none of `RefinementPanel`'s required props: `pendingAction`, `conflict`, `currentRevisionNumber`). The deck review page fires `POST /api/drafts/{draftId}/refine` directly and detects completion the same way `handleRegenerateDesign` already does: capture the slide's `exportUrl` as a baseline, poll `GET /api/decks/[id]`, and treat a changed `exportUrl` (or a `REGENERATE_TIMEOUT_MS` elapse) as settled. `GET /api/decks/[id]` gains one derived boolean per slide (`hasPendingConflict`) so a conflict can end the spin immediately instead of running out the timeout.

## Architecture

```
GET /api/library
  ├─ Draft query (existing, + deckSlide:null)  ──┐
  ├─ Deck query (new, deckVisibilityWhere)       ├─→ mergeLibraryItems() → { items, total, page, pageSize }
  └─ (both windowed to page*pageSize, sorted desc)┘
                                                        │
                                                        ▼
                                          Library page renders PostCard | DeckCard
                                          per item.type

Deck review page (/decks/[id])
  DeckReviewSlideCard (+ refine input) ─POST /api/drafts/{draftId}/refine─→ (existing route, untouched)
  handleRefine() tracks baseline exportUrl + hasPendingConflict,
  same polling loop as handleRegenerateDesign
```

## Data Model Changes

None. No new columns, no migration. `hasPendingConflict` is derived at read time from the existing `Draft.pendingConflict` column (already used by the single-draft refine flow); the merged library list is a query-time composition of two existing tables, not a new persisted shape.

## API Changes

- **`GET /api/library`** — response shape changes from `{ drafts: DraftRecord[], total, page, pageSize }` to `{ items: LibraryItem[], total, page, pageSize }`. `total` becomes `filteredDraftCount + filteredDeckCount`. **Breaking for any caller of the old `drafts` key** — the only in-repo caller is `src/app/(app)/library/page.tsx`, updated in this change. `page`/`pageSize`/`search`/`status` query params are unchanged.
- **`GET /api/decks/[id]`** — each entry in `slides[]` gains `hasPendingConflict: boolean`. Additive, no existing field removed or renamed.
- No other route's request or response contract changes. `POST /api/drafts/[id]/refine` is called from a new client site but its contract is untouched.

## Key Decisions

1. **App-code merge over a DB-level `UNION`.** Fetching `page*pageSize` rows (not an independent `skip`/`take` per source) from both `Draft` and `Deck`, sorting each descending by `createdAt`, then merging and slicing to the requested page is the simplest approach that is still _correct_ at page boundaries — an independent `skip` per source would skip or duplicate items whenever the two sources interleave across a page edge. This re-fetches earlier pages' worth of rows on every request, which is fine at this app's team-scoped item counts (explicitly called out as the accepted tradeoff in the proposal) and avoids a much messier raw-SQL union across two differently-shaped tables.
2. **Decks ignore the status filter, respect search.** `READY`/`SCHEDULED`/`PUBLISHED`/`FAILED` are per-post statuses with no clean 1:1 deck equivalent (a deck can be "READY" in the sense every slide is exported, but that's a derived, not stored, concept, and doesn't compose with `SCHEDULED`/`PUBLISHED` at all since decks aren't published as a unit). Showing decks unconditionally except via search keeps the filter's meaning unambiguous for both item types; can be revisited if this is confusing in practice.
3. **Thumbnail = first EXPORTED/PUBLISHED slide by `orderIndex`, else placeholder.** Matches the existing pre-export `PostCard` placeholder behavior exactly, and avoids showing a slide that isn't representative of the deck's final ordering (e.g. slide 3 finishing before slide 1).
4. **`DeckCard`'s export-enabled gate uses `readySlideCount === slideCount`, never `deck.status`.** Grounding surfaced that `Deck.status` never actually transitions to `GENERATING` or `READY` in the current implementation: `generateDeck.ts`'s approve path leaves it at `OUTLINE_READY` deliberately ("deck.status is left untouched (still OUTLINE_READY) so the route can be [retried]"), and no other code path advances it. `DeckStatus.READY`/`GENERATING` exist in the enum but are dead states today. This means the deck review page's own `DECK_STATUS_TO_CHIP` map is already effectively showing "draft" for every approved-and-generating-or-finished deck — a pre-existing gap, **not fixed by this change** (out of scope), but one this design must not build on top of. `DeckLibraryItem` therefore carries `readySlideCount` alongside `slideCount` so the Library tile can compute real readiness the same way `DeckReviewExportBar` does today (from live per-slide status), without waiting on a broader fix to the Deck status machine.
5. **Refine is a new, deck-scoped UI control, not a reuse of `RefinementPanel`.** `RefinementPanel` is built around the single-draft page's richer poll payload (`pendingAction`, `conflict` object with explanation, `currentRevisionNumber`) which the deck poll intentionally doesn't carry (see the deck page's own comment on why regenerate-design uses exportUrl-diffing instead of a pendingAction field). Building a second, smaller control that mirrors the UX but matches the deck poll's actual shape is simpler than either bolting deck semantics onto `RefinementPanel` or growing the deck poll to fully mirror the single-draft one. The suggestion-chip list is shared (`refineSuggestions.ts`) to avoid drift between the two.
6. **Brand-kit conflict surfaces as a redirect, not an inline override.** The single-draft page has a full Override flow (`overrideConflictId` + the withheld HTML echoed back). Building that same override UX twice — once generically, once per-slide — is unwarranted scope for v1; a slide-level conflict is rare (kit compliance issues), and "go resolve it on the post's own page" reuses the existing, already-correct Override flow without duplicating it. `hasPendingConflict` is a boolean specifically so the withheld HTML/explanation never has to leave the single-draft route's existing trust boundary.

## Risks & Mitigations

- **Risk: pagination correctness at the two-source boundary.** Mitigated by making the merge a pure, directly unit-tested function (`mergeLibraryItems`) with an explicit boundary-straddling test case, rather than trusting an ad hoc inline merge in the route handler.
- **Risk: `total` drifting from the real filtered count** if the two count queries and the two list queries use different `where` clauses. Mitigated by building each source's `where` once and reusing it for both its `findMany` and its `count`, exactly as the existing Draft-only code already does.
- **Risk: deck items accidentally gaining post-only actions** (Publish/Clone/hard-delete) if the Library page's per-item render branch is wrong. Mitigated by the `type` discriminator being required and exhaustively switched on (TypeScript union), so a missing branch is a compile error, not a silent fallthrough.
- **Risk: a conflicted refine silently spinning until timeout**, confusing anyone who didn't know to check the slide's own page. Mitigated by FR-11 — `hasPendingConflict` ends the wait immediately with an explicit message, no schema change required since the underlying data already exists on `Draft`.
- **Risk: scope creep into deck deletion/archival or Path A deck support.** Explicitly out of scope per the proposal; not touched by any task in this change.
