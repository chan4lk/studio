# Design: PowerPoint (.pptx) slide export from brand kit designs

**Change:** pptx-slide-export
**Created:** 2026-08-03

## Technical Approach

Mirror `POST /api/generate/export` (`src/app/api/generate/export/route.ts`) almost exactly for auth/visibility/render-if-missing, then add one new step: fetch the export PNG's bytes server-side and hand them to `pptxgenjs` as a full-bleed background image on a single slide, sized in inches from the same `dimensionsFor(brief.aspectRatio)` the PNG render already used (÷96 for 96dpi). Return the generated buffer directly as the response body — no bucket upload, no DB field, no schema change. A small pure function, `buildPptxBuffer(pngBuffer, aspectRatio, notes?)` in `src/lib/export/pptx.ts`, does the `pptxgenjs` work and is the unit-test surface; the route is a thin wrapper (auth, resolve/render PNG, call the function, stream the response) matching the project's existing route-thinness convention (`docs/handoff.md`: "One design pipeline... routes are thin adapters").

## Architecture

No new architectural layer — this slots into the existing draft/export data flow as a second "packaging" step over the same rendered PNG `/api/generate/export` already produces and stores:

```
Draft.htmlContent --(renderHtmlToPng, existing)--> PNG bytes --(uploadObject, existing)--> BUCKET_EXPORTS, Draft.exportUrl
                                                       |
                                                       +--(NEW: getObjectBuffer + buildPptxBuffer)--> .pptx bytes --(NEW: streamed response, not stored)
```

Reuses, unmodified: `renderHtmlToPng` (`src/lib/renderer/puppeteer.ts`), `dimensionsFor` (`src/lib/aspectRatio.ts`), `uploadObject`/`exportKey`/`BUCKET_EXPORTS` (`src/lib/storage/minio.ts`), `canAccessContent` (`src/lib/authz/visibility.ts`), `withTeamAuth`/`parseBody` (`src/lib/api/handler.ts`).
New, this change only: `getObjectBuffer` is already exported from `minio.ts` for exactly this "server needs an object's own bytes" case (its doc comment: "color sampling, vision ingestion, re-uploading an export elsewhere") — no change needed there either, just a new caller.

## Data Model Changes

None. No new Prisma fields, no migration — the `.pptx` is generated per-request and not persisted (per the proposal's resolved open question).

## API Changes

- **New:** `POST /api/drafts/[id]/export/pptx` — team-authed, body `{}` (draft id comes from the route param, not the JSON body, unlike `/api/generate/export` which takes `draftId` in the body — the pptx route is scoped by URL param to match every other `/api/drafts/[id]/*` action route's convention, e.g. `regenerate-design`, `refine`, `clone`). Response: binary `.pptx` on success; JSON `{error}` on 404/422/500 (same shape as every other route's error responses, so the client's existing error toast handling degrades gracefully even though the success path isn't JSON).
- **No change** to `POST /api/generate/export`'s request/response contract — only its internal render-if-missing logic is extracted into a shared helper, called identically from within the same route.

## Key Decisions

- **Image-backed slide, not native shapes (v1).** Per the approved proposal: decomposing arbitrary CSS layout into editable PPTX shape geometry is lossy/fragile and a much larger effort; a full-bleed background image is deterministic, always faithful to the brand design, and reuses a render that already exists. Native shapes stay an explicit v2 candidate.
- **Slide matches the post's own aspect ratio, not a fixed 16:9/4:3.** Avoids a letterboxing decision entirely and is the simplest, most faithful mapping — resolved this way in the proposal's open questions.
- **Not persisted — generated on-demand every request.** It's a deterministic re-packaging of an asset (the PNG) that's already stored; storing a second derived artifact per draft would be schema churn for something cheap to regenerate. Resolved this way in the proposal's open questions.
- **Route is scoped `/api/drafts/[id]/export/pptx` (draft id in the URL), not `/api/generate/export/pptx` (draft id in the body).** Every other single-draft action route in the codebase (`regenerate-design`, `regenerate-copy`, `refine`, `clone`, `retry`) lives under `/api/drafts/[id]/*` — matching that convention here rather than extending the differently-shaped `/api/generate/export` endpoint.
- **Route fetches PNG bytes itself via `getObjectBuffer`, never hands `pptxgenjs` a presigned URL.** Presigned EXPORTS URLs are short-lived and the object is private; `pptxgenjs`'s image path accepts a `Buffer`/base64 directly, so there's no reason to round-trip through a URL the library would have to fetch itself. Matches `getObjectBuffer`'s own documented purpose ("server-side code that needs its own storage's bytes... re-uploading an export elsewhere").
- **Client uses raw `fetch`, not `apiFetch`, for the download.** `src/lib/apiFetch.ts` unconditionally calls `res.json()` on success — incompatible with a binary response. The existing precedent (`ImageLightbox.tsx`'s `download()`) already does exactly this pattern (raw `fetch` → `.blob()` → `URL.createObjectURL` → `<a download>`) for cross-origin MinIO downloads; this change applies the same technique to a same-origin API route instead.
- **Render-if-missing logic is extracted into a shared helper rather than duplicated.** Keeps `/api/generate/export` and the new pptx route from drifting on how a draft becomes `EXPORTED` (single source of truth for that side effect, same principle the project already applies elsewhere, e.g. `canSubmitBrief()` unifying two gates that had drifted — CLAUDE.md, PR #40 entry).

## Risks & Mitigations

- **Risk:** `pptxgenjs` output validity/rendering fidelity across PowerPoint/LibreOffice/Google Slides is not something a unit test can fully verify (a unit test only checks the buffer is a valid zip with the expected internal parts). **Mitigation:** AC-5 calls for a manual spot-check (open the generated file in at least one real viewer) as part of verification, in addition to the automated buffer-structure unit test.
- **Risk:** Extracting `/api/generate/export`'s render-if-missing block into a shared helper touches an existing, working route. **Mitigation:** pure extraction (no behavior change) — the existing route's own tests (if any) plus the new pptx E2E cases both exercise the extracted path, so a regression there would surface in either suite.
- **Risk:** Large brand-kit designs (embedded imagery) could make the source PNG large, and `pptxgenjs` base64-encodes the image into the `.pptx` XML — memory/response-size overhead. **Mitigation:** this is bounded by the same PNG the app already renders and stores for the ordinary export path (no new size ceiling introduced); out of scope to optimize further in v1.
